# 数弈 alpha —— 开发者说明

这是一个**可独立运行**的最小包：界面 + CUDA 引擎 + 当前最强模型 + 协议。
没有训练脚本、没有开发工具、没有源码；本文说明它内部是怎么设计和训练的,
以及现有训练量达到了什么水平。

---

## 1. 包里有什么，怎么跑

```
shuyi.exe                  Win32 界面（规则与显示；不含任何搜索）
shuyi_engine.exe           无头引擎：NN-MCTS，CUDA 12.4 构建
models/b4c32-s34760-d470705.bin   当前最强的阻挡规则网络（6 代，470,705 局面）
shuyi-ui.ini               随包设置：阻挡规则、A=1、512 visits、引擎同目录
ENGINE_PROTOCOL.md         引擎协议 v2（命令 + JSON 流式分析）
RULES.zh-CN.md             规则全文
```

双击 `shuyi.exe`：默认双人对弈 + 阻挡规则，同目录引擎自动加载。空格开始/停止分析，
引擎菜单里可以换模型、换规则、改访问上限和 A值。

引擎也可以脱离界面单独用（`shuyi_engine.exe` 读写 stdin/stdout）：

```
ruleset blocking
set_model models/b4c32-s34760-d470705.bin
set_engine mcts_nn
set_backend auto
1 analyze red 512 interval 100
```

`bench 256` 测吞吐，`selfplay 4 256` 让模型自己下几盘。协议见 ENGINE_PROTOCOL.md。

## 2. 架构：三个产品，一条协议

```
core/        规则：棋盘、合法性、计分、8 种对称变换
engine/      shuyi_engine.exe：搜索 + 网络 + 协议
ui/          shuyi.exe：状态权威 + 呈现；链接 core，不链接搜索
protocol/    两者之间唯一的契约
```

- 界面与引擎**分开编译、互不链接**，通过 stdin/stdout 行协议通信，所以引擎可以是另一个
  项目、另一种语言、另一台机器上的构建。界面里"选择引擎程序…"就是指向任意实现。
- 引擎是**持久化服务**：一个进程服务整盘棋，命令驱动；分析按固定间隔（默认 100 ms）
  推送 `info {json}`，包含最佳着法、胜率、目差（若有）、访问数、主变序列、逐格数据。
- 界面是**状态权威**：对局记录、合法性、悔棋都在界面；引擎只知道当前局面和它的搜索树。
  搜索树因此可以继承：`play` 把根推进到子节点，`set_visits` 不会丢掉它。
- 没有回退：引擎报 `?` 界面就显示错误，绝不自己走一步；CUDA 不可用时 `auto` 会明确
  报告 `cpu`，显式 `cuda` 则直接失败。

## 3. 规则与计分（一句话版）

9×9 共 81 格。红先，双方轮流在空格放 1–9 的数字，每种数字各 3 枚，共 54 手。
终局按"每个格子的十字邻域（自身 + 上下左右）里红黑最大数字的符号"逐格计分，
加上 A值（阻挡规则标定 +1.26，包里取整 +1）后为正红胜、为负黑胜。

**阻挡规则**：落点四邻若有异色且数字 ≥ 要下的数字，该着非法；无合法着法强制过手，
连续两次过手终局。它把"石头"变成一种占领：一个红 9 永久封死它十字里的黑方，所以
数字的使用顺序本身是策略。分支因子比现行规则小约 30%（中局）到 70%（残局）。

完整定义见 RULES.zh-CN.md。

## 4. 引擎设计

### 4.1 搜索：PUCT MCTS + 三件套

- **PUCT**：`Q + c_puct · P · sqrt(N) / (1 + n)`，先验来自网络策略头。
- **访问预算**：一次访问 = 一次模拟 = 一次网络前向。这是唯一与机器无关的预算，
  评测统一 512 visits/步。搜索只会因为预算、墙钟（仅落子/显式请求）或 `stop` 停止，
  **没有树大小上限**（历史上那个上限会在 3.5 万访问时把未终局叶子当终局，产生假 100%）。
- **对称**：每个局面用 `symmetryMask()` 现场检测 8 种二面体变换（恒等、两条轴镜像、
  两条对角镜像、90/180/270 度旋转、以及叠加）。同一轨道内的等价着法只搜索一次，
  其余着法镜像显示同一组数字（访问数也共享，否则策略目标会教网络"等价着法有优劣"）。
  每个局面都重新检测，不做全盘假设。
- **MCTS-Solver**：节点带 `provenValue / provenScore / scoreExact`。子树被完全解算
  （所有应对都解算）时把精确胜负与目差回传；根在"已解算且目差精确"时提前结束，
  剩余预算故意不花。残局因此是硬胜负、硬目差，不用网络估计。
- **根宽度**按预算定：`max(32, visits/16)`，512 visits 开 32 个根着法，
  几万 visits 会把所有对称轨道都打开（整盘 81 格都有数字），不会只剩一个点。

### 4.2 评估

网络一次前向同时给出：

- 策略 `p(a)`：81 格 × 9 个数字 = 729 维（非法着法屏蔽后归一化）；
- 价值 `v`：当前行棋方的胜率；
- 目差 `s`：可选的分数头（本包模型**未训练**该头，所以界面显示 `--`，
  只有终局精确值会显示目差——不用胜率反推目差）。

搜索用 `Q = 价值 + 少量模拟回报`，先验与价值混合比例、Dirichlet 根噪声、
温度等都是引擎参数（协议里可调的部分见 ENGINE_PROTOCOL.md）。

### 4.3 计算后端

- **CUDA**：im2col + cuBLAS 批量前向。MX350 上 b4c32 单次约 0.6–0.7 ms，
  512 visits 约 0.4–0.5 s（CPU 前向约 3.6 ms/次，512 visits 约 2 s）。
- **CPU**：OpenMP 按输出通道并行；没有 GPU 时 `set_backend auto` 明确报告 `cpu`。
- **α-β 引擎**（`set_engine pruning`）：迭代加深 + aspiration window + PVS + 置换表，
  预算解释成节点数。它是同一个二进制里的对照组，不参与本包的主力配置。

## 5. 网络形状

当前主力是 **b4c32**（4 个残差块、32 通道）：

```
输入   37 × 9 × 9   18 个棋子平面（红 1..9、黑 1..9）
                    + 9 个红方剩余手牌平面 + 9 个黑方剩余手牌平面
                    + 1 个行棋方平面
全局   22 维        双方剩余张数、已落子数、原始分、行棋方等
主干   3×3 conv(37→32) + 4 × [conv3×3 → BN → ReLU → conv3×3 → BN → 残差]
策略   1×1 conv(32→2) → 摊平成 729 维
价值   1×1 conv(32→1) + 全局 → 32 隐层 → 1（tanh）
目差   同上结构 → 1（tanh(score/30)），本模型未启用
参数   86,009（文件 344,076 字节）
```

模型文件格式（`SHUYINN3`）：magic(8) version(4) channels(4) blocks(4) inputs(4)
globals(4) flags(4) ruleset(1) + 权重。`flags` 的 bit0 表示有没有分数头；
`ruleset` 字节让引擎能拒绝"用现行规则的网络下阻挡规则"这种错误配置。

容量对比：b4c32 = 8.6 万参数，KataGo 最小的 b6c96 = 103 万（12×），
b8c128 = 241 万，b10c128 = 300 万。**容量是当前第一瓶颈。**

## 6. 训练思路

1. **自对弈产数据**：C++ 树 + 批量 CUDA 前向（`shuyi_selfplay_gpu`），
   默认 1024 visits/步、2000 局/代。落子按访问数取分布，记录策略目标与终局胜负/目差。
2. **前两代 bootstrap**：gen0 随机走子（纯策略学习），gen1/gen2 单层扫描
   （用网络的策略当目标、不做完整搜索），gen3 起才是 MCTS 自对弈。
   这样在策略还很差时不至于把搜索噪声当老师。
3. **顺次迭代、不设闸门**：第 N+1 代用第 N 代的数据、从第 N 代权重续训；
   arena 只记录不阻断。原因是闸门会被"对某个旧模型恰好强"误导，而顺次链条更简单。
4. **只用 ELO 判断强弱**，不看 val_loss：曾出现过 val_policy 从 4.40 降到 3.34
   但 200 局复核胜率 0.495 的反例。
5. **评测口径**：统一 512 visits/步，random 锚定 0，ELO 用两参数 logistic 拟合，
   90% 置信区间。A值用自对弈扫描 + logistic 交点标定（阻挡规则 +1.26，SE 0.22）。

当前这一代（blk1）：

| 项 | 值 |
|---|---|
| 代数 | 6（gen0 随机 → gen5） |
| 总优化步数 | 34,760 |
| 累计局面 | 470,705（每代约 7.8 万） |
| 训练超参 | 40 epoch、batch 512、lr 2e-3（余弦） |
| 模型 | `b4c32-s34760-d470705.bin` |
| ELO（阻挡，512 visits，random=0） | **+1520** |
| A值 | +1.26（包内取整 +1） |
| 目差头 | 未训练（显示 `--`） |

## 7. 已知短板与下一步

1. **容量**：8.6 万参数对 729 维策略明显不够。下一步 b6c96（103 万）起步。
2. **分数头未训练**：目差目前只在解算的残局精确；训练 `--score-weight` 需要带分数场的
   SYSELF4 数据，属于下一轮。
3. **残局表**：最后 4–6 手的完全解算可以离线生成/在线查表，能把"已解算"的比例再推高。
4. **开局**：没有开局库；开局靠网络先验 + 搜索，对称性让前几手很快收敛。
5. **界面**：当前 alpha 只有 Win32；协议是语言无关的，其他前端可以直接写。

## 8. 怎么验证这个包

```bash
# 协议一致性（任何引擎都能跑）
python protocol/tests/protocol_smoke.py  shuyi_engine.exe
python protocol/tests/visit_budget_smoke.py shuyi_engine.exe

# 引擎侧自检
echo -e "ruleset blocking\nset_model models/b4c32-s34760-d470705.bin\nset_engine mcts_nn\nbench 256\nquit" | shuyi_engine.exe
```

包内没有训练/评测脚本；需要复现训练或跑 ELO 时用仓库里的 `training/` 与 `tools/`
（`training/pipeline.py` 是流水线入口，`training/elo.py`/`arena.py` 是评测）。
