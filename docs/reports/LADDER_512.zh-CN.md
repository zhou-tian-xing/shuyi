# 512 visits 阶梯：给第二张表打底

2026-11-26 22:20 → 11-27 08:23，RTX 3080，10.0 小时。目标是把 64 visits 之外的
第二张表（512）从零建起来，并且回答两个问题：512 的绝对分可不可比，64 的排序能不能代替它。

## 怎么分配局数

一组对局能给出的精度是 `n = (1.96 · 173.7 / h)² / (p(1−p))`，价钱完全由 `p(1−p)` 决定。
所以规则不是"每组 300 局"，而是：

- **已经够准的不给局**；
- **打不出两面结果的不打**：预期胜率 > 0.985 的对，再多局也是 3000-0，而一边倒的格子
  `decisive()` 根本不收，对评分零贡献；
- **锚点不豁免**：`b6c96-s2800 ↔ random` 是零点的唯一来源，给到最大份额 2,000 局。

结果：45 组 + 3 条补边，**24,800 局**，紧的对中位精度 **±26 Elo**。
每一格都保住了败局——最悬殊的 `s2800` 对 `random` 是 1954-46（97.7%），仍然两边都赢过。

## 512 比 64 高，而且高得不均匀

同一批 38 个模型在两张表里的差：

| 位置 | 64 | 512 | 差 |
| --- | ---: | ---: | ---: |
| 最高 `s346359` | +2716 | +2982 | **+265** |
| 中段 `s253603` | +2651 | +2922 | +271 |
| 低段 `s8160` | +1165 | +1214 | +49 |
| 最低 `s2800` | +472 | +651 | +179 |

中位差 **+220**，最小 0（`random` 自己），最大 +299。

**这不是"64 测错了"，是零点本身在动**：`s2800` 对 `random` 在 64 下是 93.0%（465-35），
在 512 下是 97.7%（1954-46）。搜索帮模型、不帮随机，所以"离随机有多远"随预算增长——
**绝对分天生依赖预算，报数必须带上 visits。**

## 排序呢：64 基本能代替，顶端不行

- 名次位移：**平均 1.1 位，最大 7 位**（38 个模型）。
- 前 5 名重合：**3/5**。

所以：**排序用 64 够用**，前几名之间（互相差 20–40 分、CI ±30）还是得看 512。

## 一个必须记下的坑：断开的表照样出分

第一次并表后，512 表是**三段互不相连**的：`s2800` 只和 `random` 打过，因为它在 64 表里
通往主链的那条边要经过 `b4c32-s5960`，而那个模型已经不在服务器上了。中间的
`{s10840, s13520, s14680}` 也是孤岛。

断开的图不会报错——先验把 38 个模型全按 0 附近压平，评出来跨度只有 1,000 分，
**最弱的 `s2800` 排在第一名**。补三条边（`s2800↔s5480`、`s8160↔s10840`、`s14680↔s31536`，
共 1,300 局）之后才连成一块。

现在 `leaderboard.py` 会先算连通块：只给含锚点的那组定分，并把被丢下的模型名字打出来。
`components()` 早就写好了，只是从来没被调用过。

## 以后怎么用

| 用途 | 用哪张 | 代价 |
| --- | --- | --- |
| 排序、找异常、训练监控 | **64** | 每 300 局约 50 s |
| 对外口径、前几名分胜负、定版 | **512** | 每 300 局约 7.7 min |
| 新模型晋升 | 两张都补，只补它的边 | 64 一条、512 一条 |

`pair_budget.py` 会读现有表算差额，所以每次只补"还不够准"的那些对，不会重测已经够准的。

## 复现

```bash
python training/pair_budget.py --table runs/leaderboard/matches_64.csv \
    --budget 23500 --visits 512 --keep '^b6c96-' --cap 2000 \
    --plan runs/analysis/plan_512.json
# 服务器上：
bash runs/diagnosis/ladder512.sh
```
