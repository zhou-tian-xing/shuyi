# 为什么最近一轮变慢：证据、图、以及下一步

2026-11-26。对象是 `b6c96-nopass-20261125c`（8 小时 9 代）和新跑完的
`b6c96-nopass-20261126a`（11 小时 12 代）。

## 先说结论

1. **变慢是真的，幅度也不小。** 同一协议（64 visits、nopass、A=+0.5、300 局端到端）下，
   上一轮涨 **+402 Elo**（273-27，91.0%），这一轮涨 **+144**（209-91，69.7%）。
2. **但证据不支持"模型太小、已经到顶"。** 权重自己在数据量曲线上仍在上升：当前 2710，
   拟合渐近线约 +3110（见下图）。真正的瓶颈还没有被测量过。
3. **最实在的解释是训练信号有三处缺陷。** 三处都已核实并修好，它们同时压低两轮的效率，
   并让"这一代是否更好"的判据失真。修好之后才谈容量和架构。
4. **架构（nested bottleneck / transformer）现在没有证据。** 现有网络是普通残差 CNN；
   要不要换，必须用冻结语料 + 匹配算力做对照，而这正是需要 GPU 的那一步。

## 两轮的可比数字

| 量 | 25c（8 小时） | 26a（11 小时） |
| --- | ---: | ---: |
| 完成代数 | 9 | 12 |
| 墙钟 | 7 h 17 m | 10 h 59 m |
| 新产出对局 / 局面 | 19,647 / 1.02 M | 24,384 / 1.27 M |
| 优化步 | 92,170 | 126,117 |
| 自对弈速率 | 0.849 局/s | 0.754 局/s |
| 端到端直接对局 | 273/300（91.0%） | 209/300（69.7%） |
| 直接增量 | **+402** [+334, +470] | **+144** [+102, +187] |
| 每小时增量 | 55 | 13 |
| 每 100 万新局面的增量 | 394 | 114 |

每代配置几乎没变（2,183 → 2,032 局；26 → 27 epoch；1024 visits；3 个并发对局组），
所以落差不是"这一轮少训了"。

## 图怎么看

- 一个圆点一份本地权重（共 58 份，其中 45 份在 64 visits 榜上有分）。横轴是文件名里的
  累计局面数（对数），纵轴是同一张榜拟合出的 Elo（`random = 0`）。
- **同一架构同色**：`b6c96` 33 个点（4 万 → 323 万局面，+472 → +2710），
  `b4c32` 12 个点（8 万 → 60 万，+551 → +1941）。实线是每种架构各拟合的一条逻辑斯蒂。
- 拟合优度：b6c96 的 RMSE 是 **51 Elo**，b4c32 是 **36 Elo**。
  若把 45 个点混在一起只拟合一条，RMSE 升到 **113–124 Elo**——不同架构的数据经济不同，
  不能共用一条曲线，这也是图里分色分线的原因。
- 渐近线是**假定**的（取该架构最好点 +400），不是拟合出来的：它决定曲线末段有多平，
  所以只用来读"离拐点还有多远"，不用来预测极限。
- 带白圈的 15 个点是 2026-11-26 用同一份对局记录复测过的同条件点；其余来自历史榜，
  其规则与 A 值没有逐条核验（`runs/analysis/scaling/elo_vs_data.csv` 里逐份列出）。

读法：b6c96 的曲线在 16 万局面附近过膝点，之后每增加 3 倍数据大约 +150 到 +450，
**仍在上升**，没有出现"再加数据也不动"的平台。所以"数据白喂了"这句话目前没有证据。

## 三条候选解释，各自的证据

### 一、模型太小（容量）

- 现状：b6c96 只有 **1.03 M 参数 / 83 M MAC**，6 个残差块 × 96 通道。
- 反证：曲线仍在上升；而且仓库里那份 `b10c128`（1.4 M 参数、234 万局面、经典规则）
  **从未进过任何一张可评分的表**，所以"更大的模型没用"从来没有被测过。
- 判定：**未测量**。这需要固定语料 + 从零初始化 + 匹配算力的 b6c96 vs b8c96 对照。

### 二、数据与训练信号（证据最硬）

三处缺陷，都已在本机核实并修好：

1. **从 `.bin` 续训时评分头被重置。** `load_bin` 解析了 `has_score` 标志却只读到
   `value_fc2.bias` 就停，6 个 `score_*` 张量从不读取；`load_state_dict(strict=False)`
   又恰好放过它们。于是每一代都在用随机初始化的评分头重新学"预测分差"，
   而它的损失照常回传到共享主干（`--score-weight 0.5`）。已修并加了往返测试。
2. **训练掩码不执行阻挡规则。** 阻挡规则是**落子**规则，nopass 同样保留它：
   一格周围四邻若有更大的敌方数字，就不能落更小的数。`make_legal_mask` 只看
   "空格 + 手里还有" —— 一块敌方 9 在中心时，掩码给出 **720** 个可行动作，
   规则上只有 **684** 个。占 5% 的概率质量落在引擎永远不会走的着法上，
   标签平滑也往那里分；顺带把 target 统计里的"合法着法数"分母也弄大了。已修。
3. **两个 shard 的 game id 都从 0 开始。** 拼接后不同世代的"第 0 局"被当成同一局，
   按局划分时把无关对局编到一组；日志里的 `games=2032` 实际是 4,064 条轨迹。
   重算默认种子后：**每一代 122 条验证轨迹里有 112–118 条是上一代训练过的**，
   所以验证损失不是"没见过的数据"上的损失。已修（按 shard 加偏移）。

另外一处更正：26a 的第 0 代**用了回放**（25c 末代 shard + 新 shard，219,149 行），
早先报告写的"第 0 代无回放"是错的。

这几条在两轮里同时存在，因此**不能单独解释 25c → 26a 的落差**；但它们会同时压低两轮的
效率，并且让"哪一代更强"的判断依赖一个被污染的验证集。

### 三、架构不足（nested bottleneck / attention）

- 现在的网络：两段 3×3 卷积的 post-activation 残差块，无 BN，policy / value / score 三头，
  输入 37 平面 + 24 全局量。理论感受野 27×27，**已经覆盖 9×9 棋盘**——
  所以 attention 的假设应该是"内容相关的全局协同"，而不是"看得更远"。
- 文献只能支持"值得测"，不能预先判胜负：KataGo 记录单层 3×3 bottleneck 在等算力下更差、
  两层以上才有效；ChessBench 的 CNN 基线自己声明未调优，不能当作"CNN 不如 transformer"的证据。
- 判定：**排在容量对照之后**。原生推理器目前是固定层序的图，nested 和 attention
  都需要新的导出与 CPU/CUDA 支持，先做 PyTorch 侧诊断更省时间。

## 建议的顺序

1. **用修好的这版先跑 3–4 代**（约 3 小时），确认验证损失回到"第 1–2 个 epoch 见底"且不再靠重叠数据；
   端到端对局要给出 +>0 的增量。
2. **冻结语料**：用当前最强权重生成 4,400 局（`train_resnet.py` 之外的一步，约 1.7 GPU 小时、约 0.7 GB），
   其中 400 局留作永不见于训练的对照。
3. **容量 × 数据量对照**：b6c96 与 b8c96（1.32× MAC）分别用 2,000 / 4,000 局从零初始化训练，
   同 seed 两个复本；判据同时看验证损失与 64 visits 对局。
4. **只有第 3 步显示"加宽无益"时**，才做 nested / attention 的等算力对照。

统计上要知道的：300 局在五五开附近的 95% 区间约 **±39 Elo**，要分辨 20 Elo 需要约
**1,160 局**。所以第 3 步的对局预算不能只给 300 局。

## 需要什么设备

一台 **RTX 3080 或同档**、能跑 8–12 小时：

- 冻结语料 4,400 局 ≈ 1.7 h；
- 8 个 5–10k update 的离线对照 ≈ 0.6 h（按历史 10.5k update ≈ 4–5 min 估）；
- 64 visits 对局：每 300 局约 50 s，若每次 4 组对照 × 2 复本 × 2 数据量 × 2 架构 ≈ 1 h；
- 末代 1024 visits 复核：每 100 局约 4 min。

第 4 步（nested / attention）另算，且要先在 PyTorch 里做到输出对齐。
