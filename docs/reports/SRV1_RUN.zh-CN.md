# srv1 实跑记录（RTX 3080，2 小时 09 分，7 代）

机器：RTX 3080 10 GB（compute 8.6）、16 核、31 GB 内存，Ubuntu 22.04 + CUDA 12.4 + torch 2.4.1。
代码：[`training/pipeline.py`](../training/pipeline.py) + [`tools/selfplay_gpu.cpp`](../tools/selfplay_gpu.cpp)。
全部产生局面与训练都在 GPU 上，没有 Python MCTS、没有 CPU 推理。

```bash
bash training/server_setup.sh          # 编译 + 单测 + CUDA/CPU 校验 + 平面校验 + 基准
python3 training/pipeline.py --run-name srv1 --generations 7 --oneply-gens 2 \
        --games-per-gen 2000 --batch-games 512 --visits 1024 --root-k 32 --top-k 16 \
        --arena-games 160 --epochs 40 --batch 512 --channels 32 --blocks 4 --komi -5
```

## 1. 引导链是有效的

gen0 只学价值（policy 目标老实地均匀），policy loss 5.70、top1 0.7%——等于随机落子。
一层扫描两代之后：policy 4.61 → 4.42，top1 **29.7% → 44.0%**，对上一代分别拿下 0.988、0.838。
**先验不是搜出来的，是"全宽一层扫描"做出来的**，这条路径走通了。

## 2. 一层扫描在第 3 代饱和

gen3 = 0.494、gen4 = 0.475：1 层视野能提供的信息用完了（policy loss 还在缓慢下降 4.304/4.306，
但棋力不再涨）。这正是应该切到 MCTS 的信号，切点选对了。

## 3. 但 MCTS 代没有换来棋力——**val loss 掉了，胜率没涨**

gen5/gen6 的训练指标是全跑最好的：

- val loss 4.40 → **3.34**（−24%）
- 目标 `cell_ratio` 0.77 → **0.60**（目标更锐利、更能区分格子）
- 目标峰值 0.147 → **0.190**

可是对 gen2 的 200 局复核是 **0.495 / 0.5125**，完全在噪声里（200 局 σ≈3.5%）。
原因：MCTS 目标更"尖"，网络更容易拟合，但**尖 ≠ 对**——它学的是"这一代搜索认为哪个好"，
而这些搜索本身没有比一层扫描更强。

> 这就是必须只用 arena 判强弱的原因。这次的 val loss 曲线会骗人，arena 没有。

## 4. komi −5 是错的（本次最大的问题）

用 gen2 自对弈（512 visits，160 局）测颜色平衡：

| komi | 红 | 黑 | 平 | 红胜率（除去平局） |
|------|----|----|----|------|
| **0** | 75 | 68 | 17 | **52.4%** |
| **−5** | 16 | 131 | 13 | **10.9%** |

即公平 komi ≈ **−0.3**，不是 −5。之前的 "−4.5…−6" 是用退化网络（b2c16，64 visits，接近乱下）标出来的，
换成真会下的网络后整个标定都变了。

后果：本次 gen1..gen6 的**六成以上对局在开局前就被颜色决定了**——价值目标几乎是常数
（红方 ≈ 0、黑方 ≈ 1），价值头学不到"怎么赢"，只学到"黑方赢"；arena 也因此更吵。
策略目标没受影响（它来自访问计数），所以 policy 该涨的涨了。

**已改**：`--komi` 默认 −5 → **−0.5**（`training/pipeline.py`、`training/run_generation.sh`）。
注意价值头编码了 komi，换 komi 必须重训，不能沿用旧模型。

## 5. 晋升门太紧，等于第 2 代之后停摆

160 局 σ≈3.9%，0.55 的门要求真实提升 ≥+9% 才有一半概率通过。gen3..gen6 的候选与 gen2 差距
都在 ±0.03 内，于是全部 KEEP，模型停在 gen2。做法本身没错（宁可保守），但这条曲线说明：

- 想要持续爬升，arena 至少要 400 局、门槛 0.52；或改成"不劣于就接受"；
- 或者每代都从当前最佳继续训练（现在就是这么做的），接受后置评分。

## 6. 吞吐与真正的瓶颈

| 项目 | 实测 |
|------|------|
| 前向（b4c32，batch 1024） | 104,180 evals/s |
| 一层扫描一代（2000 局） | 6.5 min（≈210k evals/s，批量大、GPU 吃满） |
| MCTS 一代（1500 局 × 1024 visits） | 25.5 min（≈51k sims/s） |
| 训练一代（108k 局面 × 40 epoch） | 1.5 min |
| arena（160 局 × 1024 visits） | 3 min |

MCTS 只有 ~51k sims/s，而前向能到 104k：`nvidia-smi` 显示 **GPU 利用率 27%、CPU 20%**，
两个都没吃满——瓶颈是**串行**：每 tick 先 CPU 下降、再等一次 CUDA 调用（batch 512 约 5 ms）、
再 CPU 展开回传（约 4 ms）。下一步是双缓冲：把 tick N 的展开/回传与 tick N+1 的 GPU 调用重叠，
理论上能到 ~1.9 games/s（现在 1.0）。这不是架构问题，是实现里还剩的一段流水线。

## 6.5 事后用 ELO 重排：第 2 代之后是一条平台

之前用"和上一代打 160 局"判断强弱，噪声 ±4%，所以看起来是 0.494 / 0.475 / 0.534 / 0.494——
分不清。现在用 `training/elo.py` 把 7 代模型（外加旧的 b2c16）放进一个循环赛，
每对 24 局、64 visits、换色、带先验的最大似然 + bootstrap：

| 模型 | Elo | ±90% | 战绩（168 局） |
|------|----:|------|------|
| gen4 | **+375** | [329, 450] | 126/0/42 |
| gen3 | +341 | [304, 402] | 120/0/48 |
| gen6 | +330 | [265, 397] | 118/0/50 |
| gen2 | +324 | [269, 385] | 117/0/51 |
| gen5 | +319 | [267, 374] | 116/0/52 |
| gen1 | −238 | [−325, −170] | 49/0/119 |
| v2-old（旧部署 b2c16） | −645 | [−745, −563] | 19/0/149 |
| gen0 | −805 | [−939, −731] | 7/0/161 |

读法：

1. **引导链值 +567 Elo**（gen0 → gen1，一层扫描第一次生效）；
2. **gen1 → gen2..gen6 再 +560 Elo**；
3. **gen2..gen6 的区间互相重叠，点估计最大的是 gen4**——第 2 代之后就是平台，
   多跑的 4 代（2 代 oneply + 2 代 MCTS）总共 ≈ 0 Elo。之前"gen2 最好"的结论是噪声，
   "MCTS 白跑"的结论也只是噪声；正确的说法是**这段完全没有提升**；
4. 两小时的新流程比旧部署模型高 ≈ 970 Elo。绝对 Elo 依赖参赛池（锚点是池内均值）
   和先验，跨池不能直接比；**只有同一池内的差距有意义**，且这组样本的差距不确定度约 ±100。

推论：卡住的不是容量（3M 参数的 b10c128 在本机池里还打不过 90k 的 b4c32），
而是**数据质量**（komi −5 造成的单边对局）和**目标分辨率**（64 visits 的测量、1024 visits 的自对弈）。
下一轮先把 komi 修好、把 MCTS 的 visits 提到 2000+，再用 ELO 看曲线有没有真的抬起来。

## 7. 这次证明了什么 / 下次怎么排

**已证明**

1. `random → oneply → MCTS` 的引导链能从零训练出可用策略（top1 44%），全程 GPU；
2. 目标健康闸门按设计工作：gen1 之前用未训练的网做一层扫描会被判 `cell_ratio 0.99` 拒绝；
3. arena 是唯一可信的强弱判据，val loss 会骗人；
4. 全流程 2 小时 09 分跑完 7 代、68 万局面，可复现（manifest + 日志 + 模型名带 steps/data）。

**下次（同样 3 小时）应该这样排**

1. `--komi -0.5`（先跑 150 局自对弈确认红黑接近 50/50，再开跑）；
2. `--oneply-gens 2`（第 3 代开始只会 0.49，别浪费 20 分钟）；
3. MCTS 从第 3 代开始，`visits 1024 / root-k 32`，`games 1500`；
4. `--arena-games 400 --promotion-threshold 0.52`；
5. 想要更多代就把 `games 1000`，别降 visits（本次 1024 的目标 `cell_ratio` 0.60，400 时是 0.85）。
