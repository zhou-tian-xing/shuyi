# 训练失效诊断（2026-11-22）

## 结论先说

b10c128 学不动**不是**模型容量问题、也不是数据分布问题，而是**训练目标里没有信息**：

自对弈每步只跑了约 **11 次模拟**（10 ms ÷ CPU 单次前向 ≈ 0.9 ms），而平均合法着法有 **347 个**。
C++ MCTS 的选择顺序是「先展开未访问的子节点」，所以 11 次模拟 = 把先验最高的 11 个着法各访问一次，
**搜索根本没有比较过任何一个着法**；再叠加根节点的 Dirichlet 噪声（0.25），这 11 个候选里有一部分是随机的。
于是存进数据集的 policy target 是「某个数字的 ~11 个任意格子上的均匀分布」——它与局面无关，任何网络都学不会。

## 证据

### 1. 旧数据集的 target 统计（`runs/b10c128_3h/gen_000`）

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| 每次模拟访问到的格子数 | **10.9** | 每步只有约 11 次模拟 |
| 平均合法着法 | 347.2 | 搜索预算比分支数小 30 倍 |
| target 熵 | **2.484 nats**，p10 = p90 = 2.48 | 恰好等于 ln(12)，分布形状固定 |
| 有效着法数 | 12.1 | 目标只区分 12 个着法 |
| 单一数字上的质量 | **98.1%** | 先验被 `hand_bias`（只看数字、不看位置）主导 |
| 访问格子的平均扫描序 | 26.0（随机 39.5） | 候选集来自先验顺序，不是 Q 值 |
| value 均值/标准差 | 0.500 / 0.479 | 结果接近抛硬币 |

`p10 = p90 = 2.48` 是最直接的证据：所有局面的目标分布形状完全一样，
说明它不是「搜索出来的」，而是「按先验顺序数出来的」。

### 2. 训练曲线（`docs/b10c128_run/training_b10.log`）

```
epoch 1/50  train=4.9801 val=4.5251 policy=4.4214 value=0.2075 top1=0.021 top5=0.101
epoch 50/50 train=3.8245 val=3.8830 policy=3.7532 value=0.2595 top1=0.024 top5=0.117
```

* policy loss 收敛到 **3.753 ≈ ln(42.5)**，即网络输出≈均匀分布；
* top-1 从 2.1% 到 2.4%，等于 1/合法着法数，**没有任何提升**；
* value MSE 从 0.2075 涨到 **0.2595 ≈ 0.25 = 抛硬币的方差**，即只学到了基准胜率；
* train ≈ val（3.82 vs 3.88），说明**不是过拟合，是数据本身没有信号**。

网络做得很对：它把目标拟合到了目标自身的熵。错的是目标。

### 3. 规则/胜负判断

用 `training/verify_rules.py` 把旧 shard 的每一局从 ply 2 重放到 ply 53，
逐点比对棋盘、手牌数量、先手方：375 局全部一致；终局比分与 C++ 的 value 一致率 96%
（剩余差异来自数据集不保存第 54 手，无法唯一复原）。结论：**胜负判断与棋子/手牌规则没有错**。

## 三个真正的 bug

1. **搜索预算小于分支数**。`--time 10` 在 CPU 单线程前向下只够 ~11 次模拟；
   「先展开未访问节点」的策略让搜索退化成枚举先验前 11 名。
2. **噪声进了训练目标**。根节点 Dirichlet 噪声在展开时就混进先验，
   随后被原样存成 policy target；在 11 次模拟下噪声无法被 Q 稀释，等于往标签里加随机数。
3. **蒸馏 + 重复训练冒充换代**。15 个 generation 全部用固定的 b2c16 当老师，
   数据分布从未改变；每一代只是把同一份噪声重新拟合一遍，这不是换代。

## 已实施的修复

* `training/gpu_selfplay.py`：**多局批量 GPU 推理的 MCTS**。
  每局仍然每个模拟节点一次网络前向，但把 N 局的叶子拼成一个 CUDA batch，
  所以 64–256 次模拟/步在 3080 上是可负担的。
* **保证 sims ≫ root_k**：根节点只保留先验最高的 `root_k` 个候选，
  内部节点 `top_k`，模拟次数远大于候选数，Q 项才会真正参与排序。
* **噪声只用于探索，且在候选截断之前**（否则候选集就是扫描序前 N 格）。
* **除 gen0 外禁止蒸馏**；每代只用当代数据，不回放旧代。
* **评估**：GPU 批量 arena（交替黑白、上百局），而不是只跟 random/pruning/mcts 打。

## 为什么 b2c16 的「ELO 598」不可信

那个 ELO 是在 `random,pruning,mcts` 和 v1 上算出来的。一个 policy 近似均匀、
value 近似 0.5 的模型，只要比随机落子稍好，就能在这些对手身上拿到很高的相对分。
评估对手太弱、局数太少，指标被放大了。

## 下一步（需要更长的机器）

```bash
python training/gpu_selfplay.py --model models/gen_000.bin \
  --games 3000 --sims 256 --root-k 32 --top-k 16 \
  --out runs/v3/gen_000/selfplay/shard_000.bin
python tools/train_resnet.py --input-planes 37 --channels 128 --blocks 10 \
  --data runs/v3/gen_000/selfplay/shard_000.bin --init-model models/shuyi_resnet_v2.bin \
  --epochs 20 --lr 1e-3 --out runs/v3/gen_000/candidate.bin
```

gen0 允许从旧模型热启动（19→37 平面 stem 零填充），gen1 起必须用当代模型自对弈。

## 修复后的目标对比（实测）

同一批 20 局、相同网络（b2c16）作为对手：

| 指标 | 旧（10 ms / ~11 次模拟） | 新（GPU 批量 / 64 次模拟，root_k=8） |
| --- | --- | --- |
| 每步访问的着法数 | 10.9（覆盖 347 个合法着法的 3%） | 8.0（候选集内） |
| target 最大概率 | 0.0865（均匀是 0.090） | **0.2334**（均匀是 0.125） |
| 有效着法数 | 12.1 | 7.2 |
| target 熵 | 2.484（恒定） | 1.977（随局面变化） |

旧目标的 max prob 比均匀分布还低，说明它**就是噪声**；新目标的最大概率接近均匀的两倍，
说明 Q 值真正参与了排序。`training/verify_rules.py` 同时确认规则/比分与 C++ 一致。

### 附加发现：先手优势过大

修复后的 3000 局自对弈里红方胜率 **66%**（komi = 1.0）。这不是训练问题，是规则参数问题：
`aValue` 太小，导致先手明显占优。后果是 value 头必须花容量去学「颜色先验」，
评估也必须交替黑白（arena 已这样做）。建议把 komi 调到红方胜率接近 50% 再长期训练。
