# 数弈引擎架构

本文先冻结引擎主线的大结构，再进入实现。后续微优化不应改变这里的边界：
状态表示、置换表、MCTS 树、UI/引擎进程协议和 ELO 评测。

## 1. 进程与目录边界

```
┌─────────────────────────────┐      协议 v2：命令 + JSON 流    ┌──────────────────────────────┐
│ shuyi.exe                   │  stdin/stdout, 一行一条消息     │ shuyi_engine.exe             │
│ 原生 Win32 UI（ui/）        │ <────────────────────────────> │ 无头引擎（engine/）          │
│ - 棋盘/落子/悔棋：状态权威  │   = … / ? … / info {json}       │ - 搜索/网络/分析/走棋/bench  │
│ - 读线程 + 100ms 刷新 Timer │                                 │ - 单搜索线程，可被 stop 中断 │
│ - 只持有“展示用”分析快照    │                                 │ - 弱状态：只知道当前局面     │
└─────────────────────────────┘                                 └──────────────────────────────┘
              │                                                              │
              └────────────── 都只链接 core/（规则）────────────────────────┘
```

- 两个产品**分开编译、互不链接**：UI 链接 `core/`，引擎链接 `core/` + 自己的搜索。
  界面里没有任何搜索代码，引擎里没有任何 Win32。
- 契约只有 [protocol/ENGINE_PROTOCOL.md](../protocol/ENGINE_PROTOCOL.md)：命令表、
  `info` JSON 字段、流式语义、错误与版本规则。引擎可以被换成一个完全不同的实现。
- 引擎持久运行（一个进程服务整盘棋），不是每步新开进程/线程；分析按 interval
  （默认 100 ms）持续推送 JSON，UI 用 100 ms Timer 重绘，约 10 Hz。
- 对局记录归 UI；引擎只知道“当前局面 + 该局面的搜索树”。树的继承因此是同一个
  局面 key 的延续，`play` 把根推进到子节点，`set_visits` 不会丢弃它。
- 搜索只会因为三种原因停下：访问预算、墙钟（仅落子/显式请求）、`stop`。

## 2. 规则状态：`Position`

`Position` 是规则层唯一真源，同时服务 UI、GTP 引擎、循环赛和测试。

内部由三部分组成：

1. `board_[81]`：`+1..+9` 红子，`-1..-9` 黑子，`0` 空。用于快速单格读取与计分。
2. bitboard：
   - `empty_`：81 位空格；
   - `occupied_[2]`：红/黑占用；
   - `number_[2][10]`：每种颜色每个数字的棋子位图。
   bitboard 用于合法着法生成、终局判断、NN 特征和未来增量评估。
3. `zobrist_`：落子/悔棋时 XOR 增量维护的棋子哈希。`key()` 再混入行棋方，作为 TT 键。

不把 MCTS 的树节点和状态混在一起。树节点只存“从父节点走到这里的着法”和统计量；模拟时用可撤销的 `Position` 走路径。

## 3. 剪枝引擎与置换表

- 算法：迭代加深 Alpha-Beta；根节点保留最佳着法与 PV，并通过进度回调输出
  `depth/nodes/score/best`。叶节点在“黑方走完”的红方回合评估，评估纳入稳定格、
  边界格和双方剩余手牌。
- 深度只按“完整回合”递增：红方根搜索 2/4/6… 层，黑方根搜索 1/3/5… 层，
  避免在红方刚下完的奇数层评估。
- 由于每层约 700 个合法着法，纯全宽深搜在 650 ms 内只能到 2 层左右。
  当前使用选择性束搜索：根最多 32 个、深层最多 16 个候选（按 TT/PV/静态分排序），
  在 650 ms 下可到 4 层；`rootBranching/maxBranching=0` 可切回全宽。这是有意的
  强度/深度折中，不是“忘记加深”。
- 置换表 `TranspositionTable` 是独立类：
  - 固定大小、2 的幂、直接索引；
  - entry 保存 `key / depth / bound(EXACT/LOWER/UPPER) / value / best move / age`；
  - 每次新搜索递增 generation，深搜优先替换浅层旧项；
  - 值统一为“轮到走棋的一方”的视角。
- 根节点使用 **aspiration window（渴望窗口）**：第一次完整迭代后在上一轮分数
  周围开 ±24 分的窗口；若 fail-low/fail-high，则把窗口翻倍并把当前最佳着法
  钉到根着法序列首位重搜。只有窗口内精确完成的一轮才会替换上一轮结果，
  超时/中断不会把半轮搜索写回结果。
- 根和内部节点都使用 **PVS 零窗口**：第一个着法用完整窗口，后续着法先用
  `[alpha, alpha+1]` 侦察；只有超过 alpha 才用完整窗口重搜。`window/wres/pvs`
  会随 `info` 输出，便于确认窗口搜索实际生效。
- TT 由 `AlphaBetaEngine` 跨手持有；`think()` 临时搜索使用临时 TT。
- 大架构约束：TT 不放进 `Position`，也不把 PV 存在 TT 之外的单例里；搜索函数接收 `TranspositionTable&`。

## 4. MCTS：SoA 与树复用

MCTS 采用 **Structure of Arrays**，避免每个节点一个 `std::vector<Child>` 的对象开销：

```
nodeMove[]        每节点对应着法
nodeParent[]
nodeFirstEdge[]   该节点在全局 edge 数组中的起点
nodeEdgeCount[]
nodeVisits[]
nodeValueSum[]    从该节点行棋方视角的累计值
nodeTerminal[]

edgeMove[]        全局边数组（SoA）
edgeChild[]       -1 表示尚未展开
edgeVisits[]
edgeValueSum[]    从父节点行棋方视角的累计值
edgePrior[]       NN 先验 / 均匀先验
```

- 每个节点只展开一部分候选：有 visit 预算时根宽度为 `max(32, visits/16)`
  （512 visits 最多开 32 个轨道，5000 visits 最多开 312 个），墙钟模式才用
  `mctsRootChildren=64`；内部节点默认最多 `mctsMaxChildren=48` 个，最后
  `mctsFullWidthPlies=6` 手不再剪宽。早期版本在根节点展开全部 729 个合法着法，
  在短时限下会把访问全部耗在根层；现已改为有限根宽度。
- 子节点按需创建：先建 edge，首次选中时再分配 child 节点。
- 树复用：`genmove/analyze` 结束后根节点保留。实际落子调用 `advance(move)`；若该着法在根边中，根移动到对应子节点，否则整棵树重置。
- 分析快照从根节点的边统计生成；除 `moves` 前几个候选外，还生成 81 格
  `cells` 推荐（推荐数字、胜率、访问数、平均终局分）。根节点保留全部着法边，
  但只有有限子集可被搜索选中，因此 UI 能展示所有点而搜索不被 729 宽根拖死。
- 值统一用“父节点行棋方视角”存边统计，回溯时逐层翻转，避免根/子视角混用。

## 5. MCTS + NN

- 策略价值网络是一个独立接口 `PolicyValueNet`，当前实现是 KataGo 风格 ResNet：
  - v1/v2：19 个 9×9 平面（18 个石头平面 + 行棋方平面），22 维全局向量；
  - v3：37 个 9×9 平面（0–17 石头、18 行棋方、19–36 双方手牌计数），22 维全局向量；
  - v4：仍是 37 个平面，全局向量扩到 24 维，末尾是 A/10 与 |A|/10，
    这样 A 才是网络的输入，而不只是终局判定的一部分；
  - 输出：729 个 `(格子,数字)` 的 policy logits + 一个 value（当前行棋方胜率）；
    可选分数头输出终局 raw score；
  - 通道数/残差块数不是编译期常量：模型头记录 shape，C++ 运行时按头加载。
    仓库里的 b4c32 是 32 通道 × 4 块，v1 基线是 16×2。
- 网络推理只发生在 MCTS 的扩展/叶评估点；当前 value 已不再与随机 rollout 平均
  （`nnValueBlend=1.0`），以缩短短时限下的 NN 评估成本。
- 权重从外部文件加载。`set_model` 会拒绝与当前规则不匹配的模型；缺少可加载模型时
  `mcts_nn` 直接拒绝搜索（`ready()`），不会静默假装有 NN。
- `shuyi_selfplay` 用 MCTS 自对弈生成数据：根节点 Dirichlet 噪声、根访问分布作为
  policy target、终局胜负作为 value target；GPU 版还写终局 raw score 供可选分数头使用。
  `training/train_resnet.py` 训练并导出 C++ 二进制权重。
- `info` 行携带 `nn=文件名`；v3 模型报 `a_input=0`，v4 模型报 `a_input=1`。

## 6. GTP-like 协议

引擎进程从 stdin 读命令，stdout 输出。命令成功以 `=` 开头，错误以 `?` 开头；分析流是 `info ...` 行。

首批命令：

```
protocol_version
name
version
list_commands
boardsize 9
clear_board
set_engine random|pruning|mcts|mcts_nn
set_time 650
set_a 1
play red e5 5
genmove red
analyze red
stop
quit
```

`info` 行示例：

```
info engine=pruning depth=4 nodes=12000 window=24 wres=0 pvs=9 score=+5 winrate=0.68 best=e5:7 pv=e5:7,c4:3
info engine=mcts visits=20000 winrate=0.57 best=e5:7 moves=e5:7:0.57:9000,c4:3:0.21:3000
```

- `score` 是当前行棋方视角的分数（含 A值），用于剪枝展示。
- `winrate` 是当前行棋方的期望得分（胜 1、平 0.5、负 0）。
- `moves` 只带根节点前若干个候选，供 UI 画胜率分布。
- `genmove` 结束输出 `= e5 7`；`analyze` 持续输出 `info`，直到 `stop`。
- 所有搜索在独立工作线程；主线程继续读 `stop`，所以 UI 永远能取消。

## 7. ELO 评测

统一以 **随机走子引擎为 0 分基准**。

- 循环赛工具 `shuyi_tournament` 在进程内直接调用引擎接口，避免管道开销。
- 每对引擎按先后手交替对局，使用固定 seed 集合，结果可复现。
- 记录 `W/D/L`；ELO 用固定随机基准为 0 的 Bradley-Terry/Logistic 拟合。
- 置信区间用对局 bootstrap（重采样对局、重新拟合）得到 95% 区间。
- 输出机器可读 CSV 和 Markdown；时间控制、每对局数、引擎版本写入报告头。
- 因为对局数有限，ELO 区间可能很宽；报告中必须同时给出局数和 CI，禁止只报一个点估计。

## 8. 实施顺序

1. `Position` bitboard + Zobrist，保持现有规则测试全绿。
2. `TranspositionTable`、剪枝引擎接口和 GTP 进程骨架。
3. MCTS SoA + 树复用 + 分析快照。
4. NN 接口、模型加载、MCTS-NN 路径。
5. UI 引擎进程管理、10Hz 分析面板。
6. ELO 循环赛、文档和完整测试。

## 9. 当前实现状态

- `Position` 已有 81 位双字 bitboard、Zobrist 增量键、增量计分和 `validate()` 自检。
- `TranspositionTable` 是独立类，剪枝引擎跨手持有；`think()` 使用临时表。
- `shuyi_engine.exe` 已实现命令循环、搜索工作线程、`stop` 取消、`info` 100ms 节流。
- UI 通过 `CreateProcessW` + 匿名管道启动引擎；reader 线程入队，100ms Timer 消费并重绘。
- MCTS 节点/边使用 SoA；`onPlay()` 尝试把根推进到对应子节点，失败则重置。
- MCTS-NN 使用 KataGo 风格 ResNet：v1/v2 是 19 个输入平面（18 石头 + 行棋方），
  v3/v4 是 37 个（再加 18 个手牌平面）；全局向量 v3 为 22 维、v4 为 24 维
  （末尾 A/10 与 |A|/10，这样 A 才是网络的输入而不只是终局判定的一部分）。
  策略头输出 729 个 `(格子,数字)` logits，价值头融合双方手牌、行棋方、当前局面分、
  手数、空格数。仓库基线模型 `models/shuyi_resnet_v1.bin` 是 16×2，
  随包发布的 `models/b4c32-*.bin` 是 4 块 32 通道；
  服务器训练脚本默认 32×4，导出格式相同。
- 根节点支持 Dirichlet 噪声；`shuyi_selfplay` 以根访问分布为 policy target、
  终局胜负为 value target 生成 v2 数据，`training/train_resnet.py` 用 PyTorch
  训练并导出 C++ 可直接推理的二进制权重；`training/pipeline.py` 负责
  15 代自对弈、训练、双模型晋升的编排。
- 当前默认融合为 `0.5 * policy + 0.5 * uniform`、纯 value head
  （`nnValueBlend=1.0`）；MCTS-NN 根宽度按 `max(32, visits/16)` 自动开
  （512 visits 为 32），内部节点 `mctsMaxChildren=48`，最后 6 手不剪宽。
- 剪枝叶节点在“黑方刚走完、轮到红方”的位置评估；评估函数区分已稳定格和边界格，
  并把双方手牌中的高数字潜力纳入 `handWeight` 项，避免只在红方刚落子后做静态判断。
- ELO 工具已实现随机基准、先后手交替、随机开局、Bradley-Terry 拟合和 200 次 bootstrap CI。

### 异步协议的一个细节

`genmove` 为了允许 `stop` 不被阻塞，采用两段响应：

```
=                      ← 命令已被接受
info ...               ← 搜索过程
= e5 7                 ← 最终着法
```

客户端不能把第一个空 `=` 当成最终着法。UI 侧用 `g_enginePending` 标记，只接受
带坐标/数字的最终行。`analyze` 同样先返回空 `=`，之后一直推 `info` 直到 `stop`。

## 10. 分支因子实测：NN-MCTS 5000 visits/步（阻挡规则）

> 本节给出一局由 `mcts_nn` 以 **5000 visits/步** 生成的阻挡规则对局的分支统计。
> 逐手原始数据在 [reports/branching_5000v.csv](reports/branching_5000v.csv)，
> 汇总在 [reports/branching_5000v.json](reports/branching_5000v.json)。

一句话结论：本局**合法分支因子平均 317.9**；按“对局中每手新增 5000 visits”的口径，
**根搜索宽度 28.2、有效分支因子 2.47**。同一局面如果清空树、独立做 5000 visits，
中盘（ply 10/20）的有效分支因子可到 **45.9 / 66.3**，到残局才降到 2–4——所以
2.47 是“树复用下的每手增量”口径，不是“5000v 搜索天然只有两个候选”。

### 10.1 口径

一局棋里有两种完全不同的“分支因子”，本节分开报告：

| 名称 | 定义 | 说明 |
|---|---|---|
| 合法分支因子 \(b_{\text{legal}}\) | 每手 `position.legalMoves().size()` 的算术平均 | 规则允许多少种 `(格,数字)`；与搜索无关 |
| 根搜索宽度 \(b_{\text{root}}\) | 本手在根节点新增访问过的**对称轨道**数 | 搜索实际碰到的根候选数；是 \(b_{\text{eff}}\) 的上界 |
| 有效分支因子 \(b_{\text{eff}}\) | \(\exp\left(-\sum_i p_i\ln p_i\right)\)，\(p_i=\Delta N_i/\sum_j\Delta N_j\) | 根访问分布的 perplexity；等价于“与当前访问分布熵相同的等概率选择数” |

其中 \(\Delta N_i\) 是**本手新增**的根访问数，按 `Position::symmetryMask()` 合并等价着法后统计。
用新增访问而不是累计访问，是为了回答“这 5000 visits 实际花在哪些分支上”；引擎在对局中复用树，
根节点通常已经带着上一手搜索留下的访问，累计值会把那部分算进来。
测量方式是每手在 `search()` 前后各取一次 `rootPolicy()`，按轨道对访问数做差；
不是从 UI 的 `info` 行反推。

如果“有效分支因子”被理解为“搜索树实际触及的根候选数”，对应的就是 \(b_{\text{root}}=28.2\)；
本文把 \(b_{\text{eff}}\)（访问熵）单独称为有效分支因子，因为它更接近“搜索实际在比较多少个候选”。

补充口径：

- 所有均值都是这局 54 手上的**算术平均**，不是多局平均；中位数同时给出。
- `legalMoves()` 不含强制过手；如果出现无合法落点，`legal=0` 而 `searchMoves=1`。
- 被终局证明的手，搜索可能提前结束；这类手不参与模拟均值，其 `rootPolicy` 也可能
  只返回已证明的一步，单手增量不可直接比较。
- 对称轨道按引擎 `representative` 同样的规则合并；空盘 729 个着法会先塌缩成 135 个轨道。

### 10.2 对局设置

生成方式：一个一次性 C++ 探针直接链接 `shuyi_search`，用 `makeEngine(EngineKind::MctsNn)`
每手调 `search({visits=5000})`，把 `analysis.best` 落到 `Position` 并调 `onPlay`；
不经过 UI 或协议层。这样每手的 `rootPolicy()` 都能在搜索前后各读一次。

| 项 | 值 |
|---|---|
| 引擎 | `mcts_nn`，CPU |
| 模型 | `b4c32-s34760-d470705`（v3：37 平面、22 维全局、`a_input=0`） |
| 规则 | blocking |
| A 值 | 1.26（阻挡规则的标定公平值） |
| 预算 | 5000 visits/步 |
| 根噪声 | 无（`rootDirichletAlpha=0`） |
| 树复用 | 开启；每手 `onPlay` 推进根节点 |
| 落子选择 | 每手取访问数最大的着法 |
| 随机种子 | 20261123 |
| 对局 | 54 手；终局 raw = 5，加 A 后 +6.26；红胜 |
| 耗时 | 平均 21.1 s/步，合计 19.0 min（1139.1 s） |

b4c32 是 v3/A-blind 模型：A=1.26 只进入终局 `finalScore` 和精确证明，中盘的 policy/value
并不读 A。所以这局棋的“公平 A”只对最后几手的精确结果有意义，不能把它当成
A 条件化网络的行为。

### 10.6 树复用对照（fresh root）

对局中的根通常是上一手搜索展开过的内部节点，最多只有 `mctsMaxChildren=48` 条根边；
本手新增的 5000 visits 可能只碰其中一部分。为了区分“树复用造成的集中”和
“网络 policy/value 本身造成的集中”，在同样的局面、同样的 5000 visits 下，清空树再搜一次：

这 6 个抽样点的 fresh \(b_{\text{eff}}\) 为 7.00 / 45.92 / 66.29 / 10.80 / 3.52 / 2.45，
中位数约 8.9；它们不是全 54 手的平均，只说明“中盘从空树搜”比“对局中增量搜”宽得多。

`fresh root` 的根宽度上限由 `max(32, 5000/16)=312` 决定，而不是上一手留下的 48；
它更接近“打开一个局面单独分析”的行为。对局中的 `b_root/b_eff` 则包含树复用的影响。

因此两列描述的是同一局面的两种搜索状态，不能当成同一棵树的两次测量。

### 10.7 解读

1. **合法分支是规则属性，搜索分支不是。** 本局 \(b_{\text{legal}}\) 平均 317.9，
   与随机对局的 303 同量级；但按“对局中每手新增访问”的口径，\(b_{\text{eff}}\) 只有 2.47。
   这不是“阻挡规则让合法着法变少”，而是搜索把访问集中到了少数主线上。
   不过 10.6 的 fresh-root 对照说明：同一局面从空树搜 5000 visits 时，中盘
   \(b_{\text{eff}}\) 可以到 11–66；2.47 这个数主要是树复用 + 每手增量造成的，
   不能直接推广成“5000v 搜索本身只有两个候选”。
2. **访问高度集中。** 平均 top-1 份额 0.846、top-8 份额 0.972；
   在 5000 visits 下，policy 先验较尖（根先验是 `0.5*policy + 0.5*uniform`，
   合法着法越多，uniform 分量越小，非 top 先验越低），PUCT 的探索项又与子节点
   访问数成反比；访问一旦集中到少数线，其余分支的 \(U\) 迅速变小，搜索就从
   “铺开候选”转为“沿最看好的线加深”。
3. **树复用会进一步压低增量分支。** 首手空盘有 135 个对称轨道；之后根是上一手展开过的
   内部节点（最多 48 条边），本手新增访问往往只覆盖其中一部分。fresh-root 对照表
   给出了同一局面从空树重搜的结果，两者不能混用。
4. **终局是例外。** 最后几手被证明后，搜索可能提前结束或只剩验证访问，
   \(b_{\text{root}}=b_{\text{eff}}=1\)；非证明手的均值 2.55 更能代表中前盘。
5. **这是单局样本。** 表中的“平均”是这一局 54 手的平均，不是多局分布；
   换一局、换一个模型或换一个 visits 预算，数字都会变。它适合用来判断数量级和
   搜索形状，不适合当作 Elo 或强度的估计。

## 11. 终局精确性：哪部分混合，哪部分是阈值

有两个机制，不是一个：

1. **混合（一直在跑）**：搜索树展开到终局时，该节点不再问网络，直接用规则算出的
   `finalScore` 作为值并标记 `proven`（`mcts.cpp` 的 `terminal_[node]` 分支）；
   每次模拟结束后，证明沿访问路径向上爬（`updateProof`）：只要某个节点**有一个**
   子节点是"对手必败"，它就是必胜；要判"必败"则必须所有着法都生成过（`complete_`）
   且都已证明。这条路径对任意剩余手数都有效。
2. **精确求解（阈值）**：最后 6 手干脆不走 MCTS，直接全宽极小极大（`solveEndgame`），
   每一手都拿到精确目差。这是"分开"的部分，原因是 MCTS 的证明停在第"一条"必胜线就
   不走了，而目差要求把每条线都算完。

**阈值是量出来的，不是拍的**（`tools/research/endgame_cost.cpp`，4 个随机合法局面/档）：

| 剩余手数 | 节点数 | 用时 | 250k 预算够不够 |
| ---: | ---: | ---: | --- |
| 5 | 270 – 20k | 0.4 – 71 ms | 够 |
| 6 | 2.2k – 79k | 5 – 158 ms | 够 |
| 7 | 15k – 1.84M | 20 ms – 3.9 s | **不够（3/4 放弃）** |
| 8 | 310k – 8.8M | 0.6 – 25 s | 不够（2/4 放弃） |
| 9 | 1.3M – 未解出 | 1.7 s – 34 s+ | 不够 |

所以：**搜索前**的精确解算只在 ≤6 手触发（预算 250k，最坏 160 ms）；
**搜索后**再给 7 手一次机会（预算 2M，1–4 s），拿到就发布、并缓存在这个局面上
（反复展开分析不会重复付这几秒）。8 手起不触发——20 秒的"精确"对一个交互界面
不是答案。

这就是"落子前 5k visits 没有精确解、落子后立刻有"的原因：落子前剩 7 手，命中不了
≤6 的闸门，而 5k visits 的树也不可能证明 7 手（约 50^7 个节点，且树在 7 手时仍在
按 top-k 剪枝，`complete_` 为假，必败证明根本无从谈起）；落子后剩 6 手，直接进
精确解算。现在 7 手也会解：**只要 2M 节点内解得出来**。
