# 十小时自动训练计划（3080，2026-11-25）

一句话：**每代的数据量和梯度步数由模型规模决定，窗口只决定能跑几代。** 上一轮 375 局/代
（19,499 局面、1,440 步）对 103 万参数的网只是噪声；这一轮按 1M 参数的下限配：**每代
约 15–16 万局面、约 1 万步**，十小时跑 6 代。

## 1. 规模怎么定，不是拍脑袋

`training/budget.py` 做三件事，输入全是实测数字：

| 输入 | 来源 |
| --- | --- |
| 自对弈速率 games/s | `run_session.sh` 先用真实模型、真实 visits 跑 24 局测出来 |
| 训练速率 samples/s | 默认 2 万（V100 实测 3 万，3080 同量级；写低了只会更保守） |
| 参数规模 M | 从模型文件大小算（`(bytes-36)/4`），不是写死的 |

规则（写进代码，不靠记忆）：

- 目标梯度步数随参数线性放大：`target_steps = 10,000 × (M / 1.03)`；
- 训练集不是只有本代的分片：回放窗口 2 代，所以每代的训练量是「本代局面 × 1.8」，
  预算里按 1.8 倍算时间（漏掉这一项就是十小时计划跑成十二小时的原因）；
- 窗口先扣掉 15 分钟开箱和 12 分钟收尾，再除以「一代的时间」得到代数；
- 一代少于 800 局就拒绝（这正是"静默偷懒"的形状），窗口不够就报错，不缩水。

3080 上的预期（按 0.58 局/s、1024 visits 推算，实测后由脚本重新算）：

| 项 | 数值 |
| --- | ---: |
| 代数 | **6** |
| 每代对局 | **2,177**（≈113,000 局面） |
| 每代 epoch | 27（训练集 ≈ 204,000 局面，含回放） |
| 每代优化步 | **10,287** |
| 每代耗时 | 91 分钟（自对弈 82、训练 4、arena 4） |
| 合计 | 13,062 局 / 679,000 局面 / 61,722 步 / 9.6 小时 |

对照上一轮：**每代数据 ×6、每代步数 ×7、总步数 ×21**。

这些数字是脚本在机器上实测后重算的，不是我拍的表：这台 3080 的自对弈是
**0.455 局/s**（1024 visits、batch 32），比上一台 3080 记的 0.58 慢。探针必须用
**运行时的 batch**——用 8 局一批测出来是 0.25，会把整个会话按"半速的卡"定规模。

## 2. 一条命令

```bash
cd /root/shuyi
HOURS=9.6 \
MODEL=models/b6c96-s25920-d258451.bin \
RUN_NAME=b6c96-nopass-20261125a \
SHUYI_PYTHON=/home/vipuser/miniconda3/bin/python \
bash training/run_session.sh
```

脚本做四件事，之后**不需要人盯**：

1. 用真实模型和 visits 跑 24 局，测出这台卡的 `games/s`；
2. `budget.py` 把窗口换算成「代数 × 每代局数 × epoch」，写进 `runs/training/<run>/plan.json`；
3. 启动 `pipeline.py`，带 `--max-hours`；
4. 每代照常：自对弈 → 过闸门 → 训练 → 和上一代打 100 局 arena → 命名入库。

`--max-hours` 是硬保险：**在代与代之间**检查，剩下的时间不够跑完下一代的 1.15 倍就停，
所以永远不会出现"跑到一半断电、模型只写了一半"。停之前在 manifest 里写
`stopped_early`（原因、代数、已用分钟）。

## 3. 无人值守的边界

| 会自己处理 | 会停下来报错（不会静默降级） |
| --- | --- |
| 时间到点，在代之间停 | 自对弈 0 局面 |
| 目标分布不达标（`cell_ratio` 等） | 目标过于接近均匀 |
| 训练中断后 `--resume` 接着跑（run 目录已有 manifest 时脚本自动加） | 模型形状/规则不匹配 |
| 显存不够时由 torch 自己报 OOM | 找不到模型或二进制 |

最后两条是故意的：这类错误重试也没用，报错比"跑出一堆垃圾模型"便宜。

## 4. 我只看前 20 分钟（初期调试清单）

1. `plan.json`：速率、代数、每代局数是否和本节表格一致（差太多说明探针被打扰了）；
2. 第一代自对弈的 `batch games=N/3038` 行：`games/s` 是否 ≥ 0.5（掉到 0.3 说明卡被抢或
   散热降频，此时应该改跑 5 代而不是硬撑）；
3. 第一代训练：`epoch 1/19` 的 `time=` 是否 ≤ 8 秒（对应 2 万样本/s 量级）；
4. 第一代 arena：和 `s25920` 打 100 局，胜率 ≥ 45% 才算"没把原来的东西训坏"；
5. `nvidia-smi` 显存：batch 512 + 96 通道应在 3 GB 以内。

之后只在每代结束时看一行 arena 结果；有异常（连续两代 < 40%）再介入，否则不动。

## 6. 风险与处置

| 风险 | 处置 |
| --- | --- |
| 3080 只有 10 GB，96 通道 batch 512 OOM | 脚本不自动降 batch：改成 `batch-games 16` 重跑第一代，别让 OOM 混进无人值守时段 |
| 机器没装 torch | `bash training/server_setup.sh --skip-apt` 先装/验，再跑 |
| 速率低于 0.4 局/s | 计划会自动少跑一代；若第一代就 <0.3，停下来换机 |
| 想中途加代 | 脚本带 `--resume` 重跑同一 `RUN_NAME` 即可，会从断点继续，计数器接着数 |

## 7. 不做什么

- 不蒸馏：每一代只用上一代自己下的棋（上一轮的 375 局是自对弈，这次只是把量补上）；
- 不为了"多跑几代"把每代砍回几百局——那是这轮要修的问题本身；
- 不用 val loss 判断强弱，只看 arena 和之后的 ELO 梯子。

## 8. 开箱时踩到的两个坑（已修，记录）

1. **探针的 batch 和运行不一致**：探针用 `--batch-games 8` 测出 0.25 局/s，运行时是
   batch 32（0.455 局/s），等于把整个会话按"半速的卡"定规模。现在 `BATCH_GAMES`
   同时传给探针和 pipeline。
2. **上传说文件带 CRLF**：Windows 工作区的 `.sh` 是 CRLF，直接 `put` 上去会让
   `set -euo pipefail` 报 `invalid option name`，看起来像代码 bug。现在 `ssh.py put`
   对 `.sh/.py/.md/...` 一律按 LF 写入，部署归档也走同一规则。

另外这台机器上的 CUDA 二进制是从别的卡（V100, sm_70）拷来的，跑起来是
`no kernel image is available for execution on the device`；`-arch=native` 的产物
不会因为换卡自动重编，删掉 `build/nn_cuda.o` 重建即可（`SHUYI_CUDA_ARCH=native` 是
按配置时那张卡算的）。

## 10. 十小时之后：绝对评估（V100 一小时）

把六个新模型接进 64/128 两张表，只打"新块内部 5 对 + 与旧第一 `b4c32-s42012` 的 1 对"，
其余格子沿用原来的 500 局/对数据。两次都发现同一个陷阱：**V100 上那份二进制是别的卡
（sm_86）编的，96 通道的 CUDA 前向是错的**（`--check` 报 logits 差到 13 分，b6c96 输给
b4c32 83%）；按 `-arch=native` 重编后 `--check` 差 2.7e-5，比分翻正。评测前先跑 `--check`，
否则整张表都是在量一个坏掉的引擎。

**64 visits（500 局/对）与 128 visits（300 局/对）的直接结果**

| 对局 | 64 visits | 128 visits |
| --- | ---: | ---: |
| `b4c32-s42012` vs `s31536`（第 0 代） | 261-239（52.2%） | 149-151（49.7%） |
| `s31536` vs `s42768` | 223-277 | 127-173 |
| `s42768` vs `s54000` | 204-296 | 121-179 |
| `s54000` vs `s65232` | 201-299 | 137-163 |
| `s65232` vs `s76464` | 200-300 | 122-178 |
| `s76464` vs `s87696`（末代） | 217-283 | 132-168 |

**结论（不经过任何拟合）**：第 0 代与 `b4c32-s42012` 打平（52%/50%），之后每一代都赢
上一代 54–60%，末代对 `b4c32-s42012` 累计 **+300（64 visits）/ +259（128 visits）**。
和 3080 上那场 120 局 81.7%（≈+260）对得上。

**拟合表的位置**（`runs/leaderboard/leaderboard.md`，22 个模型 + random，64 表 11,000 局、
128 表 6,920 局）：末代 64 visits **+1718 [+1671, +1776]**、128 visits **+1804 [+1745, +1879]**，
排在旧第一 `b4c32-s42012`（+1504 / +1606）之前，顺序正确。

**一个必须记住的偏差**：这张表的绝对高度会随参赛池变化——同样一局不差的旧表，
16 个模型时算出来是 +1729，补进 6 个强模型后变成 +1504。原因是拟合把池子均值放在 0，
再用 `random` 的拟合值去平移，而 `random` 自己也受先验收缩。**顺序和档间差可信，绝对高度
有 ±200 的系统误差**；要读"比随机高多少"，只能用同权重直接对局或把 `random` 钉死在 0 重新拟合
（下次改）。

### 11.1 这一次的吞吐改了什么（2026-11-25 晚）

上次十小时的账：每代 91 分钟，其中**自对弈 82 分钟**、竞技场 5 分钟、训练 4 分钟。
自对弈 23,417 sims/s，而同一张卡纯前向是 36,756 evals/s —— 差的 25–30% 是 tick 里
卡在空转：`descend(CPU) → eval(GPU) → expand(CPU)` 严格串行。详见
`docs/ENGINE_ARCHITECTURE.zh-CN.md` §12。

改动：

1. `--groups N`：N 组对局各自一个线程、一份模型实例、一条非阻塞 stream。A 组在卡上
   跑 kernel 时 B 组在 CPU 上走树。样本逐字节不变（每局 RNG 由 `(seed, 局号)` 决定），
   本机已验证 groups=1/2/4 的 shard md5 相同。
2. CUDA 端改用 pinned 缓冲 + `cudaMemcpyAsync` + 每实例一条 stream，去掉了每行 12 KB
   的 pageable 拷贝（pageable 拷贝会先把整个设备排空）。
3. 竞技场的 batch 翻倍：`match` 一次 tick 要分给两个网络，batch 32 时每个网络只有 ~16 行。
4. 自对弈默认带 `--stats`，每代日志里都有一行 `TICK_MS ... gpu=%`。

`run_session.sh` 会**先探测再决定**：用真实模型和真实 visits 分别跑 1 组和 2 组，
取 games/s 高的那个，把两次的 `gpu=` 都写进 `logs/probe_g*.log`。所以这一条命令
在 3080 上如果重叠没收益（卡本来就满），会自动退回 1 组，不赌。

看日志的第一处：

```bash
grep -E "groups=|fastest" runs/training/<run>/logs/probe_g*.log runs/training/<run>/logs/*.log
```

预期：3080 上 2 组能把 0.44 games/s 提到 0.55–0.60（+25~35%），十小时从 6 代变 7–8 代，
同样的数据/梯度规则（`training/budget.py`）会把多出来的时间换成更多局数。

### 11.2 一句话的验证（跑起来之后 3 分钟）

自对弈第一代的日志里，`gpu=` 应该比上次的单组 tick 高（上次是"卡忙 70–75%"）。
如果 `gpu=` 依然是 100% 附近并且 games/s 没变，说明这台 3080 的 CPU 或 PCIe 是瓶颈，
组数会自动退回 1，这一轮等于没改。

### 11.3 想换变量就只换一个

| 变量 | 代价 | 什么时候换 |
| --- | --- | --- |
| `VISITS=1536` | 自对弈慢 1.5 倍 → 4 代 | 想提高目标质量而不是数据量 |
| `REPLAY_GENS=3` | 每代训练 +2 分钟 → 少 200 局 | 担心遗忘、想多几步梯度 |
| `BLOCKS=8 CHANNELS=128` | 前向慢 2 倍 → 3 代 | 只在"连续 10 代没有新高"之后（见 §1.1） |

现在**不要**换网络结构：这条曲线还在涨，换大网等于把已经买到的 60 万局面重新学一遍。
