# 十小时自动训练计划（3080，2026-11-25）

一句话：**每代的数据量和梯度步数由模型规模决定，窗口只决定能跑几代。** 上一轮 375 局/代
（19,499 局面、1,440 步）对 103 万参数的网只是噪声；这一轮按 1M 参数的下限配：**每代
约 15–16 万局面、约 1 万步**，十小时跑 6 代。

## 1. 规模怎么定，不是拍脑袋

`training/budget.py` 做三件事，输入全是实测数字：

| 输入 | 来源 |
| --- | --- |
| 自对弈速率 games/s | `run_session.sh` 先用真实模型、真实 visits 跑 24 局测出来 |
| 训练速率 samples/s | 默认 2 万（V100 实测 3 万，3080 同量级；写低了只会更保守） |
| 参数规模 M | 从模型文件大小算（`(bytes-36)/4`），不是写死的 |

规则（写进代码，不靠记忆）：

- 目标梯度步数随参数线性放大：`target_steps = 10,000 × (M / 1.03)`；
- 训练集不是只有本代的分片：回放窗口 2 代，所以每代的训练量是「本代局面 × 1.8」，
  预算里按 1.8 倍算时间（漏掉这一项就是十小时计划跑成十二小时的原因）；
- 窗口先扣掉 15 分钟开箱和 12 分钟收尾，再除以「一代的时间」得到代数；
- 一代少于 800 局就拒绝（这正是"静默偷懒"的形状），窗口不够就报错，不缩水。

3080 上的预期（按 0.58 局/s、1024 visits 推算，实测后由脚本重新算）：

| 项 | 数值 |
| --- | ---: |
| 代数 | **6** |
| 每代对局 | **2,177**（≈113,000 局面） |
| 每代 epoch | 27（训练集 ≈ 204,000 局面，含回放） |
| 每代优化步 | **10,287** |
| 每代耗时 | 91 分钟（自对弈 82、训练 4、arena 4） |
| 合计 | 13,062 局 / 679,000 局面 / 61,722 步 / 9.6 小时 |

对照上一轮：**每代数据 ×6、每代步数 ×7、总步数 ×21**。

这些数字是脚本在机器上实测后重算的，不是我拍的表：这台 3080 的自对弈是
**0.455 局/s**（1024 visits、batch 32），比上一台 3080 记的 0.58 慢。探针必须用
**运行时的 batch**——用 8 局一批测出来是 0.25，会把整个会话按"半速的卡"定规模。

## 2. 一条命令

```bash
cd /root/shuyi
HOURS=9.6 \
MODEL=models/b6c96-s25920-d258451.bin \
RUN_NAME=b6c96-nopass-20261125a \
SHUYI_PYTHON=/home/vipuser/miniconda3/bin/python \
bash training/run_session.sh
```

脚本做四件事，之后**不需要人盯**：

1. 用真实模型和 visits 跑 24 局，测出这台卡的 `games/s`；
2. `budget.py` 把窗口换算成「代数 × 每代局数 × epoch」，写进 `runs/training/<run>/plan.json`；
3. 启动 `pipeline.py`，带 `--max-hours`；
4. 每代照常：自对弈 → 过闸门 → 训练 → 和上一代打 100 局 arena → 命名入库。

`--max-hours` 是硬保险：**在代与代之间**检查，剩下的时间不够跑完下一代的 1.15 倍就停，
所以永远不会出现"跑到一半断电、模型只写了一半"。停之前在 manifest 里写
`stopped_early`（原因、代数、已用分钟）。

## 3. 无人值守的边界

| 会自己处理 | 会停下来报错（不会静默降级） |
| --- | --- |
| 时间到点，在代之间停 | 自对弈 0 局面 |
| 目标分布不达标（`cell_ratio` 等） | 目标过于接近均匀 |
| 训练中断后 `--resume` 接着跑（run 目录已有 manifest 时脚本自动加） | 模型形状/规则不匹配 |
| 显存不够时由 torch 自己报 OOM | 找不到模型或二进制 |

最后两条是故意的：这类错误重试也没用，报错比"跑出一堆垃圾模型"便宜。

## 4. 我只看前 20 分钟（初期调试清单）

1. `plan.json`：速率、代数、每代局数是否和本节表格一致（差太多说明探针被打扰了）；
2. 第一代自对弈的 `batch games=N/3038` 行：`games/s` 是否 ≥ 0.5（掉到 0.3 说明卡被抢或
   散热降频，此时应该改跑 5 代而不是硬撑）；
3. 第一代训练：`epoch 1/19` 的 `time=` 是否 ≤ 8 秒（对应 2 万样本/s 量级）；
4. 第一代 arena：和 `s25920` 打 100 局，胜率 ≥ 45% 才算"没把原来的东西训坏"；
5. `nvidia-smi` 显存：batch 512 + 96 通道应在 3 GB 以内。

之后只在每代结束时看一行 arena 结果；有异常（连续两代 < 40%）再介入，否则不动。

## 5. 收尾（脚本停下后 10 分钟）

```bash
# 模型和记录
python training/ssh.py get /root/shuyi/runs/training/<run>/manifest.json runs/training/<run>/manifest.json
# 每个 models/*.bin 同上
# 对起点的确认：64 visits、200 局，最后一代 vs s25920
```

产物：`manifest.json`（每代的 samples/steps/arena/val）、`plan.json`、`pipeline.log`、
`models/b6c96-s*-d*.bin`（6 个）。分片不拉（每个 ≈ 60 MB，回放用不上）。

## 6. 风险与处置

| 风险 | 处置 |
| --- | --- |
| 3080 只有 10 GB，96 通道 batch 512 OOM | 脚本不自动降 batch：改成 `batch-games 16` 重跑第一代，别让 OOM 混进无人值守时段 |
| 机器没装 torch | `bash training/server_setup.sh --skip-apt` 先装/验，再跑 |
| 速率低于 0.4 局/s | 计划会自动少跑一代；若第一代就 <0.3，停下来换机 |
| 想中途加代 | 脚本带 `--resume` 重跑同一 `RUN_NAME` 即可，会从断点继续，计数器接着数 |

## 7. 不做什么

- 不蒸馏：每一代只用上一代自己下的棋（上一轮的 375 局是自对弈，这次只是把量补上）；
- 不为了"多跑几代"把每代砍回几百局——那是这轮要修的问题本身；
- 不用 val loss 判断强弱，只看 arena 和之后的 ELO 梯子。

## 8. 开箱时踩到的两个坑（已修，记录）

1. **探针的 batch 和运行不一致**：探针用 `--batch-games 8` 测出 0.25 局/s，运行时是
   batch 32（0.455 局/s），等于把整个会话按"半速的卡"定规模。现在 `BATCH_GAMES`
   同时传给探针和 pipeline。
2. **上传说文件带 CRLF**：Windows 工作区的 `.sh` 是 CRLF，直接 `put` 上去会让
   `set -euo pipefail` 报 `invalid option name`，看起来像代码 bug。现在 `ssh.py put`
   对 `.sh/.py/.md/...` 一律按 LF 写入，部署归档也走同一规则。

另外这台机器上的 CUDA 二进制是从别的卡（V100, sm_70）拷来的，跑起来是
`no kernel image is available for execution on the device`；`-arch=native` 的产物
不会因为换卡自动重编，删掉 `build/nn_cuda.o` 重建即可（`SHUYI_CUDA_ARCH=native` 是
按配置时那张卡算的）。

## 9. 实际结果（2026-11-25 跑完）

23:50:01 开始，08:53:40 结束（08:59:35 写完 manifest），六代全部跑完，没有触发
`stopped_early`。计划 6 × 2,177 局 × 27 epoch，实际每代 113,167–113,199 局面，
每代 11,232 步（第 0 代 5,616 步：没有回放），合计 **679,102 局面 / 61,776 步**。

| 代 | 结束时刻 | 模型 | 对上一代（1024 visits / 100 局） |
| ---: | --- | --- | ---: |
| 0 | 01:14:45 | `b6c96-s31536-d371618` | **79%**（对起点 `s25920`） |
| 1 | 02:48:24 | `b6c96-s42768-d484789` | 55% |
| 2 | 04:20:04 | `b6c96-s54000-d597968` | 69% |
| 3 | 05:52:09 | `b6c96-s65232-d711162` | 69% |
| 4 | 07:22:31 | `b6c96-s76464-d824361` | 62% |
| 5 | 08:53:40 | `b6c96-s87696-d937553` | 59% |

84 分钟一代，比预算的 91 分钟略快（训练 4 分钟、arena 4 分钟都在预算内）。

**绝对位置**（64 visits、komi 0.5、nopass、颜色交替）：

| 对局 | 比分 | 胜率 | 名义 Elo |
| --- | --- | ---: | ---: |
| 最后一代 vs 起点 `s25920`（200 局） | 168-32 | 84.0% | ≈ +290 |
| 最后一代 vs `b4c32-s42012`（120 局） | 98-22 | 81.7% | ≈ +260 |

起点 `s25920` 8 小时前和 `b4c32-s42012` 是 53%-45% 的平手（见 `runs/eval/quick-20261125`），
所以这十小时把 b6c96 从"和旧最强 b4c32 平手"推到"对 b4c32 八成胜"。这些数还是单次
直接对局，正式的 64/128 梯子要下次补。

**没拉回的**：每代约 340 MB 的自对弈分片（6 代 ≈ 2 GB）留在退租的机器上。下一次换机器
从 `b6c96-s87696-d937553` 接着练，回放窗口从新机器的第一代重新开始。
