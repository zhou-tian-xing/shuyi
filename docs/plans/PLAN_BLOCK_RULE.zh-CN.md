## 1. 新规则的实测影响（先算清楚再动手）

规则定义（本次采用的读法）：落点 `c`、点数 `n`，若 `c` 的**四邻**存在**异色**且点数 **≥ n** 的棋子，
则该着非法。其余不变（无提子、双方各 27 子、终局按 5 格十字的最大点数定胜负）。

`training/rule_probe.py`，各 3000 局随机对局：

| 指标 | 现行规则 | 阻挡·四邻 | 阻挡·八邻 |
|------|---------:|---------:|---------:|
| 合法着法均值 | 391 | **303**（−22%） | 253（−35%） |
| ply 0 / 5 / 10 | 729 / 684 / 631 | 729 / 634 / 554 | 729 / 590 / 493 |
| ply 20 / 30 | 497 / 340 | **376 / 216** | 297 / 148 |
| ply 40 / 50 | 185 / 51 | **91 / 16** | 52 / **6** |
| 对局长度 min/mean | 54 / 54.0 | 54 / 54.0 | **48** / 53.9 |
| 随机对局出现"无子可下" | 0 | 0 | 有（长度 < 54） |
| 终局 `raw == 0` | 6.1% | **5.6%** | 6.2% |
| komi 0 时红胜 | 46.6% | 45.8% | 44.6% |
| 终局分分布 | 奇数值为主（±1、±2） | 偶数值更常见（±2、±4） | 更分散（±1…±3） |

结论：

1. **中后盘分支因子大幅下降**（ply 30 从 340 到 216，ply 40 从 185 到 91）——这正是这个项目
   一直在打的东西：同样 400~1000 次访问，阻挡规则下每次访问的信息量高得多。
2. **开局几乎不变**（ply 0 的 729 完全一样，ply 10 只降到 554）。所以"先验要靠一层全宽扫描做出来"
   这条结论在新规则下**依然成立**，引导链不用改。
3. **和棋概率基本不变**（6.1% → 5.6%，在噪声内）。机制也没变：和棋 = `raw == -komi`。
   真正能消灭和棋的是**小数 komi**：komi −0.5 时两套规则的随机对局和棋率都是 **0.00%**。
4. 阻挡规则下终局分更偏向偶数值，说明"十字内双方最大点数相等"的中性格子变少了——
   因为**你不能在敌方的 k 旁边放同为 k 的子**，本地的平局更难被制造出来。

### 1.1 策略层面的变化（这才是真正的变化）

- **高点数变成"占地"工具**：一个红 9 的四邻，黑方**永远**不能落子（任何点数 ≤ 9 都被挡）。
  也就是一个 9 基本锁死它十字内的 5 个格子（除去边界和自己其它棋子），3 个 9 **最多** 15 格 ≈ 18% 的棋盘。
- **"高点数占地、低点数填充"**：红 9 旁边的空格只能由红方自己填，红方自然会用 1/2 去填，
  把 3、4 留给新的扩张点。这让每个数字的**时序价值**分开了——以前 27 个子的顺序几乎只是策略，
  现在是硬约束。
- **先手优势上升**（原则判断，需要用训练后的网络实测）：先手可以先把 9 落在中心，
  后手失去那片区域。随机对局看不出这一点（随机棋手不会利用），所以**komi 必须用训练后的网络重新标定**，
  不能用随机对局推。已知反例：现行规则下随机对局 komi 0 时红胜 46.6%，而训练后的 gen2 是 52.4%——
  偏差方向相反，标定必须用真棋手。
- **后手有补偿手段**：被 9 锁住的区域对后手是"不能进"，但后手可以用同样的 9 去锁别处，
  等价于"你锁 5 格我也锁 5 格"。所以争的是**谁先占到关键格**，不是谁锁得多。
- **终盘趋于强制**（ply 50 只剩 16 个合法着法），价值头在收官阶段会更容易学准。

## 2. 三个必须定的规则细节（会改变实现和手感）

| # | 问题 | 建议 | 理由 |
|---|------|------|------|
| A | "附近"= 四邻还是八邻？ | **四邻** | 与计分用的十字完全同构，只需一个几何原语。实测八邻把终盘压到 ply 50 只剩 **6** 个合法着法、对局最短 48 手就卡死（出现"无子可下"），并且 45° 相邻与计分无关，玩家难建立直觉 |
| B | 轮到某人但无合法着法怎么办？ | **过一手**（pass）；连续两次 pass 则终局，按当前盘面计分 | 3000 局随机对局没出现过，但训练后的棋手可能故意饿死对手；"过一手"是最小改动，且不会改变 54 子的总量上限 |
| C | 新规则的 komi | **已定：+1.26（SE 0.22）**，用 gen_005 自对弈 4 个 komi × 240 局标定；`pipeline.py --komi` 默认值按规则分开（classic −0.5 / blocking +1.3） | 随机对局推不出真棋手的偏差方向，见 1.1 |

三选一之外还有一条建议：**新规则下 `aValue` 很可能要比 −0.5 更偏黑**（先手占地优势）。
标定流程：跑 200 局同模型自对弈 → 若红胜偏离 50% 超过 5 个点 → 按 ±6%/点 反推调整。

## 3. 工程架构：一套代码两套规则

原则：**规则是运行时参数，不是模板参数**，因为它要跨越 UI / 协议 / 数据 / 模型格式。

```
include/shuyi/rules.h
    enum class Ruleset : std::uint8_t { Classic = 0, Blocking = 1 };
    struct RuleInfo { const char* name; bool blocking; };   // 名称用于协议/文件名
    bool moveLegal(const Board&, int side, Move, Ruleset);   // 唯一合法性入口
    std::vector<Move> legalMoves(const Board&, int side, Ruleset);
```

改动点清单：

1. **引擎核心**：`Position`、`Bitboard`、`Board`（各有一份 move 生成）统一走 `moveLegal`。
   热路径上是一个 `blocking` 分支，可预测，代价可忽略。
2. **搜索**：`mcts.cpp`、`ai.cpp`（Alpha-Beta）、新的剪枝引擎都从 `Ruleset` 取合法着法。
3. **协议**：`shuyi_engine` 增加 `ruleset classic|blocking`（查询/设置），
   `search_stats` 消息带上 `ruleset`；UI 通过启动参数或菜单设置。
4. **数据格式**：shard 头 `SYSELF2` → `SYSELF3`，新增 `uint8 ruleset`
   （`training/verify_rules.py`、`target_stats.py`、`train_resnet.py` 同步）。
   旧 shard 读作 classic，不重写。
5. **模型格式**：`SHUYINN2` → `SHUYINN3`，头里加 `uint8 ruleset`、`uint8 featureVersion`
   （顺便把上次 37 平面布局的坑显式化）。加载时校验，不匹配就拒绝——上次那个
   "布局改了但模型还能加载"的问题不能再出现。
6. **目录与命名**：`runs/<ruleset>/<name>/`；模型名 `b4c32-...-classic.bin` /
   `b4c32-...-blocking.bin`。
7. **UI**：菜单"规则"单选（Classic / Blocking），切换即重开一局；引擎侧 `ruleset` 一起下发。

验收：`shuyi_tests` 里加两组规则的自洽测试（合法性对称性、过一手、计分不变），
以及一条"同一 shard 在另一套规则下重放必须失败"的交叉校验。

## 4. 工作包（按依赖排序）

### P0 · 规则抽象 + 合法性入口（0.5 天）
- `rules.h` + 三处 move 生成改造 + 两组规则的单元测试。
- 验收：`shuyi_tests` 全绿；`--check` 里规则校验同时覆盖两套规则。

### P1 · 新剪枝引擎（用户指定优先）
- 现有剪枝 = 迭代加深 Alpha-Beta + TT + 静态分。新引擎要针对阻挡规则重写评估：
  - **着法排序**：优先"高点数占中心"（近似 `Δ(十字控制数)`），其次"填自己已锁定的格子"；
  - **评估函数**：静态分 + "已锁定格子数"（一个格子被我方最大点数独占且 ≥ 敌方四邻最大+1）
    + 剩余高点数数量；
  - **剪枝**：阻挡规则下"下 k 点"严格弱于"下 k+1 点"（同样的格子，k+1 挡得更多），
    可以安全地只保留每个格子的最大可用点数——这是新规则带来的**结构性剪枝**，
    能直接砍掉一半的着法。这一条要先证明（用穷举小盘验证），再写进搜索。
- 验收：同等时间内比旧剪枝强（用新 ELO 体系量，见 P4）；且 `--mode match` 能打满 100 局不崩。

### P2 · 双线训练可切换
- `pipeline.py` 增加 `--ruleset classic|blocking`，透传到 `selfplay_gpu`/`train_resnet`/`elo`；
  shard/模型打标签；`runs/<ruleset>/`。
- `shuyi_selfplay_gpu` 增加 `--ruleset`，`legalMoves` 走新入口；`--mode bench/check` 同步。
- 验收：一套数据只被同规则的模型消费（交叉校验失败即报错）。

### P3 · UI：方形棋子 + MCTS 三栏标记
1. **方形棋子**：`ui_win32.cpp` 的棋子绘制改成圆角矩形（半径 12%），暗色描边，
   内部按点数着色 + 数字居中；选中/hover 用 1px 高亮描边。
2. **MCTS 标记**（仅 MCTS/MCTS-NN 模式）：
   - 与棋子**同尺寸同形状**的细边框（1px）+ 半透明内部染色（alpha ≈ 96/255）；
   - 颜色：最优着法固定**浅蓝**；其余按"与最优的胜率差"映射
     `差 0 → 浅蓝`、`差大 → 红`、中间过渡到绿；实现为 HSV 线性插值（红 0° → 绿 120°），
     饱和度固定，亮度固定，避免和棋子颜色混淆；
   - **差异过大不绘制**：`胜率差 > 20%` 或 `访问数 < 最优的 5%` 的格子不画（减少噪声）；
3. **三栏文字**（每个标记内，居中，等宽小字号，行高 = 格高/3）：
   - 第 1 行：胜率（如 `62%`）；
   - 第 2 行：访问数，**不超过 4 字符**：`820`、`1.2k`、`12k`、`120k`、`1.2M`（≥10M 用 `12M`）；
   - 第 3 行：预期平均分（如 `+3.4`）；
   - 字号随格子尺寸自适应（`max(9, cell*0.22)`），GDI `CreateFont` + `SetTextAlign`，
     用 `DrawTextW` 带 `DT_SINGLELINE|DT_CENTER|DT_VCENTER`。
4. **协议**：新增 `search_stats` 行，一次推送根的所有子节点：
   `id cell number winrate visits score`（空格分隔，winrate 用千分位整数避免浮点解析）。
5. **依赖**：第 3 行的"预期平均分"需要**分数头**（见 P5）；没有分数头时该行显示 `–`
   （剪枝引擎天然有静态分，可以直接显示）。

验收：截图对比（方形棋子、三层标记、缩写正确）；`visits` 缩写单测覆盖
`999 / 1024 / 12345 / 123456 / 1234567`；关掉标记后性能不变。

### P4 · 评估改造：以随机为 0 点 + 全线路横评
1. **统一玩家接口**：`shuyi_selfplay_gpu` 增加 `--mode serve`（stdin/stdout 走现有引擎协议），
   这样 GPU 模型能和 `shuyi_engine`（random/pruning/mcts/mcts_nn）同池对战。
2. `training/arena.py`：任意两个"玩家"配对（进程或模型），换色、定 visits、写对局矩阵。
3. `training/elo.py`：新增 `--anchor random`，**把随机玩家固定为 0**（不参与拟合），
   其余模型的评分即为"相对随机落子的 ELO"；对全胜/全负的选手输出**单边下界**
   （`≥ +900`）而不是点估计。
4. 输出：一张横评表（random / pruning / mcts / mcts_nn(旧模型) / gpu:gen0..gen6），
   全部在本地跑，一次命令复现。

验收：`python training/arena.py --players random,pruning,mcts,gpu:..., ... ` 一张表；
random 恒为 0；两次运行同一配置的评分差 < 30 Elo。

### P5 · 分数头（UI 第 3 行 + 价值信号）
- 模型加第二个头：`scoreMean`（回归最终 `raw` 分，归一化到 ±1），损失权重 0.3；
- 训练目标直接用终局 `raw`（新规则下范围 ±25 左右，实测 min −22 / max +25）；
- 推理/搜索：`Node` 增加 `sumScore`，回传时按 `-` 累加，`search_stats` 直接给平均分；
- 模型格式版本 +1（与 P0 的 `SHUYINN3` 合并做一次）。

验收：验证集上 `score MAE < 3.5`；UI 第 3 行数值与终局分同量级。

### P6 · 容量爬梯（连续 10 代无提升）
- `pipeline.py` 记录每代 `elo_best`；若最近 `--plateau-generations 10` 代内
  `best_elo` 没有超过历史最高 `best_elo + --plateau-margin 20` → 触发升级。
- 升级 = 按 `--capacity-ladder "b4c32,b6c48,b6c64,b8c96"` 取下一档，
  **开新 run 目录**（宽度变了无法热启动），用当前最优模型的**已有数据**做冷启动，
  然后继续顺次训练。
- manifest 里记 `capacity_history`：{gen, blocks, channels, reason}。
- 验收：构造一个"故意不涨"的假 manifest，跑一次 dry-run 能看到升级被触发。

## 6. 风险

1. **新规则可能让先手优势过大**：如果训练后红胜 > 70%（komi −0.5 时），
   需要加大 komi 甚至改规则（例如只允许"更大"而不是"同等或更大"，或把阻挡限制在正交点）。
   这是这个计划最大的不确定性，M4 的第一批数据就能看出来。
2. **"每个格子只保留最大可用点数"的剪枝**如果证明不成立（例如不同点数影响后续可下点数），
   剪枝引擎就退回普通 Alpha-Beta，性能差一截。
3. **两条规则并行会稀释工程精力**：所以 P0 只做"参数化"，不做两套代码路径；
   任何按规则分叉的实现都要能用一行配置解释清楚。
4. **UI 三栏在 9×9 的小格子里可能挤**：先按 `cell*0.22` 字号做，若可读性不够，
   退路是只画"胜率 + 访问数"两栏，分数放到悬停提示。
