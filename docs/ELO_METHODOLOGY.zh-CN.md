# 数弈引擎 ELO 评测方法

## 1. 基准与单位

- **随机走子引擎** `random` 固定为 ELO 0。
- 其他引擎的 ELO 是相对值，不是与外部引擎可直接比较的绝对强度。
- 评测使用规则默认 `A=+1`；换 A值会改变终局结果与强度。

## 2. 对局协议

`shuyi_tournament` 在进程内直接调用统一 `Engine` 接口，不走管道，避免 I/O 影响时间控制。

- 每对引擎进行 `--games` 局。
- 先后手交替：偶数局 A 执红，奇数局 B 执红。
- 每局开头随机走 `--opening` 手（默认 2），再由引擎接管；这样同一对引擎不会反复从完全相同的开局开始。
- **每手预算固定为 visits，不用时间**：`training/evalconfig.py` 的 `EVAL_VISITS = 512`。
  时间预算在 3080 和 MX350 上是完全不同的搜索量，会让"评分"变成"主机性能测试"。
  一个 visit 的定义：MCTS/MCTS-NN = 一次模拟（一次网络前向），剪枝 = 一个节点（一次叶子评估），
  纯 MCTS = 一次 rollout。同一张表里的每个参赛者必须用同一个数。
- 使用固定 seed 派生每局种子，报告中的 seed 足以复现对局安排。
- 终局按 `A=+1` 判定；平局计 0.5 分。

### 2.1 预算一致性（硬规则）

- `shuyi_engine set_visits N` 对四种引擎都生效；剪枝引擎的 `N` 是节点预算，且**不看墙钟**
  （`SearchOptions::nodeLimit`），因此同一局面在任何机器上给同一个着法。
- `elo.py --report` 拒绝合并预算不同的矩阵，`engine/tests/visit_budget_smoke.py` 与
  `testVisitBudget` 会验证"正好用完预算"和"两次运行完全一致"。
- 训练循环内部的 arena/ELO（`pipeline.py --arena-visits`，默认等于 `--visits`）也只用 visits，
  但它只是"这一代是否变强"的判据，数值与 512 的标准表**不可混用**。

## 3. ELO 拟合

对局结果转化为 A 视角得分 `s ∈ {1, 0.5, 0}`。采用 Bradley–Terry/Logistic 模型：

```
P(A 得分期望) = 1 / (1 + 10^(-(R_A - R_B)/400))
```

以所有对局的 Bernoulli 分数似然为目标，固定 `R_random = 0`，对其余评分做阻尼 Newton 迭代。
加入极小 L2 正则，避免全胜/全负时评分发散。拟合值只依赖对局图；没有和随机或其他引擎连接时不会凭空产生评分。

两条实现约束（2026-11-26 修正，之前两条都不对）：

- **迭代必须跑到收敛，不能按固定步数停。** Newton 每一轮只能沿一条边传播信息，44 个模型的
  长链在固定 60 轮时远未收敛：测量到的分差被压缩，甚至把链顶排在第二档后面。现在以
  "一整轮里没有任何一个模型的调整超过 0.02 Elo" 为停止条件，并把最后一步的位移一起返回
  （`elo.fit_elo_checked`）；`leaderboard.py` 在没收敛时打印警告，而不是照抄一个偏小的数。
- **正则必须极小（σ = 2000 Elo）。** 原来的 σ=400 在一个跨度 2,000 分的池子里会压缩
  **测量到的**分差，而且压缩多少取决于池子里有几个模型：同一批对局，32 个模型的表里
  八小时那一段读出 +365，44 个模型的表里只读出 +140。改成 2000 后两处都读到 +150 上下
  （本轮），与端到端的直接对局 69.7%（+146）一致。它现在只负责"避免全胜/全负时发散"。

## 4. 置信区间

- 对完整对局列表做 **200 次 bootstrap**：有放回重采样对局，固定随机基准，重新拟合。
- 取 2.5% 和 97.5% 分位数作为 95% 置信区间。
- CI 反映“这组对局采样”的统计不确定性，不包含引擎版本、时间控制、开局分布变化带来的系统误差。
- 对局数越少，CI 越宽；报告必须同时给出对局数和 CI，不能只报点估计。

## 5. 当前基准结果

详见 [ELO_REPORT.md](ELO_REPORT.md)。当前一次 100 ms/手、每对 10 局的参考结果：

| 引擎 | 对局 | 胜/平/负 | 得分率 | ELO | 95% CI |
|---|---:|---:|---:|---:|---:|
| random | 30 | 0/0/30 | 0.000 | 0.0 | [0.0, 0.0] |
| pruning | 30 | 28/1/1 | 0.950 | 1375.1 | [1207.2, 1681.7] |
| mcts | 30 | 21/1/8 | 0.717 | 1095.4 | [969.0, 1188.3] |
| mcts_nn | 30 | 10/0/20 | 0.333 | 512.8 | [398.6, 589.3] |

该结果只对应：

- 9×9 数弈、A=+1；
- 100 ms/手；
- 2 手随机开局；
- MCTS-NN 使用 `models/shuyi_resnet_v1.bin`（README 中说明其训练规模）；
- 200 次 bootstrap。

不能把这张表当作“剪枝必然比 MCTS 强”的长期结论；它只是一次固定预算下的测量。

## 6. 复现

```bash
./build/shuyi_tournament.exe \
  --games 10 --time 100 --seed 20261126 \
  --nn models/shuyi_resnet_v1.bin \
  --out docs/ELO_REPORT.md \
  --csv docs/elo_results.csv
```

只跑部分引擎（仍必须包含 random）：

```bash
./build/shuyi_tournament.exe \
  --games 40 --time 50 --seed 7 \
  --engines random,pruning,mcts \
  --out build/elo_subset.md
```

## 7. 已知限制

- 随机基准很弱，因此其他引擎相对于它的 ELO 会很大；这并不表示它们接近人类高手。
- 预算很小的 MCTS 可能还没充分展开，排名会随预算变化——所以预算必须写进表里，
  不同预算的表不能合并比较。
- MCTS-NN 的强度取决于模型；`ResNet v1` 只训练了 180 局自对弈，仍是可复现的弱基线。
- 对局数有限时 ELO 区间可能很宽；报告中保留 CI 是刻意的约束。
